# 4. USER PROFILE

Crear entidad:

UserProfile

Campos recomendados:

* id
* firebaseUid
* email
* firstName
* lastName
* displayName
* phone
* status
* createdAt
* updatedAt
* lastLoginAt

Utilizar un identificador interno PostgreSQL además del firebaseUid cuando sea apropiado.

firebaseUid debe tener una restricción UNIQUE.

No permitir que un cliente cree arbitrariamente un UserProfile asociado a otro firebaseUid.

El firebaseUid utilizado para operaciones protegidas debe obtenerse de la identidad autenticada.

# 10. SUPER ADMIN

SUPER_ADMIN debe representar el nivel máximo de administración de la aplicación.

Sin embargo:

NO implementar bypasses inseguros como:

allow everything

La autorización debe seguir una política explícita.

Si SUPER_ADMIN posee todos los permisos, esto debe estar representado mediante la relación RolePermission o mediante una estrategia de autorización documentada.

No ocultar reglas críticas en código.

# 13. BRANCH AUTHORIZATION

Este punto es CRÍTICO.

Nunca confiar en:

branchId enviado por el cliente.

Ejemplo de petición maliciosa:

{
"branchId": "BRANCH-CENTRAL"
}

Si el usuario pertenece solamente a:

BRANCH-NORTE

la operación debe ser rechazada.

La autorización debe verificar la relación real:

Authenticated User
↓
UserProfile
↓
UserBranch
↓
Branch

antes de permitir operaciones sobre una sucursal.

# 14. AUTHORIZATION MODEL

Implementar conceptualmente:

User
↓
Roles
↓
Permissions
↓
Branch Scope

Una operación debe poder comprobar:

1. ¿El usuario está autenticado?
2. ¿El usuario está activo?
3. ¿Tiene el permiso necesario?
4. ¿Tiene acceso a la sucursal solicitada?
5. ¿La sucursal está activa?

Todas estas validaciones deben ocurrir antes de permitir operaciones protegidas.

# 16. CUSTOM CLAIMS

No utilizar Custom Claims como fuente principal de permisos de negocio.

Pueden utilizarse posteriormente para información pequeña y estable, pero:

Roles y permissions de negocio deberán permanecer principalmente en PostgreSQL.

Motivo:

* Pueden cambiar.
* Pueden ser numerosos.
* Requieren administración.
* No queremos depender de sincronización manual de claims.

Si se considera necesario utilizar Custom Claims para alguna función específica, documentar exactamente por qué.
