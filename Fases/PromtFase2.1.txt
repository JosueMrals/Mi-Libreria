# 1. SUSPENDED / INACTIVE USERS

Corregir:

GetMyProfile
UpdateMyProfile

Actualmente pueden ejecutarse aunque el usuario esté:

SUSPENDED
INACTIVE

Modificar la autorización para que las operaciones de aplicación protegidas solamente estén disponibles para usuarios:

status == ACTIVE

La identidad Firebase puede seguir existiendo, pero un UserProfile:

SUSPENDED
o
INACTIVE

debe ser rechazado para operaciones protegidas de SQL Connect.

No confiar en status enviado por el cliente.

El status debe obtenerse del UserProfile asociado a auth.uid.

Agregar pruebas para:

ACTIVE → ALLOW

SUSPENDED → DENY

INACTIVE → DENY

---

# 2. PRIVILEGE ESCALATION TESTING

Agregar pruebas E2E de seguridad para intentar:

1. CASHIER intenta asignarse ADMIN.
2. SELLER intenta asignarse ADMIN.
3. USER intenta modificar Role.
4. USER intenta modificar Permission.
5. USER intenta modificar UserRole de otro usuario.
6. USER intenta modificar UserBranch de otro usuario.
7. USER intenta modificar su propio status.
8. USER intenta modificar el status de otro usuario.
9. Usuario A intenta modificar UserProfile de Usuario B.
10. Usuario A intenta consultar datos de Usuario B que no debería poder consultar.

Todas las operaciones no autorizadas deben devolver DENY.

---

# 3. BRANCH ESCALATION

Agregar pruebas:

Usuario asignado a Branch A:

→ operación Branch A = ALLOW

→ operación Branch B = DENY

Intentar manipular:

branchId
userId
entityId

desde el cliente.

La autorización debe comprobar las relaciones reales de PostgreSQL.

No confiar en IDs enviados por el cliente.

---

# 4. ROLE ESCALATION

Verificar que ningún usuario pueda modificar sus propios:

role
permissions

simplemente modificando una mutation.

Un usuario no debe poder convertir:

CASHIER → ADMIN

mediante manipulación del request.

---

# 5. SUPER_ADMIN

Revisar cuidadosamente el comportamiento de SUPER_ADMIN.

No introducir:

if role == SUPER_ADMIN allow everything

como bypass de autorización.

Si SUPER_ADMIN posee todos los permisos, esto debe quedar representado por la matriz RolePermission o por una política explícita y documentada.

Agregar pruebas.

---

# 6. AUDITLOG

Verificar:

AuditLog

Debe ser append-only.

No debe existir ninguna mutation pública para:

update AuditLog
delete AuditLog

Los usuarios normales no deben poder insertar eventos arbitrarios fingiendo acciones.

Por ejemplo, un cliente no debe poder decir:

{
"action": "USER_CREATED"
}

y crear un AuditLog falso.

Los eventos deben generarse como consecuencia de operaciones autorizadas.

---

# 7. AUDIT METADATA

Revisar:

ipAddress
userAgent
correlationId

Determinar cuáles pueden obtenerse realmente desde Firebase SQL Connect/CEL y cuáles no.

NO inventar valores.

NO permitir que el cliente pueda falsificar estos campos.

Si una metadata no puede obtenerse de forma confiable en la arquitectura actual:

* dejarla nullable;
* documentar la limitación;
* explicar cómo se podrá obtener posteriormente mediante infraestructura adecuada.

Actualizar:

docs/security.md

y:

docs/threat-model.md

# 8. FIREBASE USER ↔ POSTGRESQL USERPROFILE

Revisar el problema de usuarios huérfanos.

Documentar claramente el flujo:

Firebase Auth User
↓
UserProfile

Analizar los siguientes escenarios:

A:
Firebase creation = SUCCESS
PostgreSQL creation = SUCCESS

B:
Firebase creation = SUCCESS
PostgreSQL creation = FAILURE

C:
Firebase creation = FAILURE
PostgreSQL creation = SUCCESS

No simular una transacción distribuida si Firebase Auth y PostgreSQL no la soportan conjuntamente.

Proponer una estrategia segura de:

* retry
* reconciliation
* cleanup
* idempotency

La estrategia puede quedar documentada para implementación posterior si todavía no corresponde implementarla.
